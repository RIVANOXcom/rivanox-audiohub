# Web UI preview

A responsive, five-language control-panel **prototype** is available under `web/`. It is intentionally not yet connected to a privileged device-control API.

The source includes translations for `en`, `de`, `es`, `fr`, and `it`, using browser language detection and a manually selectable language. It provides mock per-source volume, mute and 3-band EQ sliders. The preview explicitly says that audio output is unaffected.

This prevents the repository from promising a working administration interface before secure device ownership and provisioning have been implemented. Audio does not require this page to remain open.

Security requirements for the future controller:

1. Device-specific first-claim secret without a universal shared password.
2. Authenticated settings mutations and protection against cross-site requests.
3. Local-network-only exposure with a safe AP provisioning process.
4. A reset/recovery path usable without a monitor or keyboard.
5. Device state/metadata protected from unauthenticated clients.

## Read-only on-device status preview (experimental)

The image-builder installs five-language web assets under `/opt/audiohub/web` and starts an unprivileged Python HTTP service on port `8765`. **Until authenticated ownership and a protected API are available, the status preview binds to `127.0.0.1:8765` by default.** This is intentionally **not** a usable phone-based setup portal; `http://audiohub.local:8765/` is *not* available from another device in the default image. A remote browser cannot access the current local-only preview.

Only an authorized engineer testing on an isolated trusted LAN can manually configure `AUDIOHUB_STATUS_BIND_IP=<a specific RFC1918 IPv4 address>` together with `AUDIOHUB_UNSAFE_STATUS_LAN=YES` in the process environment. The image's systemd unit **does not** set this opt-in. Public, multicast, wildcard (`0.0.0.0`), link-local and hostname bind targets are rejected even with the flag. The insecure exception is **not** owner enrollment and has no sender/client authentication; never use it for production, Internet or untrusted LAN access. Disabling LAN-by-default is a deliberate security/preview usability tradeoff, not evidence of a finished consumer first-boot path.

Only GET requests for strict allowlisted UI assets and `/api/status` work. The status endpoint exposes a whitelisted, redacted subset of runtime health (USB recognized, route counts, virtual channel count and freshness), not Bluetooth addresses, SSID, credentials or settings. All POST/PUT/PATCH/DELETE requests fail closed with HTTP 405. There is no authenticated write API yet, and visual volume/EQ controls remain demonstrations.

Never forward port 8765 to the public Internet. Device ownership, authenticated controls and secure Wi-Fi provisioning remain release blockers. This experimental integration requires Pi image rebuilding and hardware validation before being considered operational.

## Browser-guided, read-only three-source layout preview (unmerged draft)

The offline five-language routing example planner now prepares an optional
**local CLI preview instruction** for the real, manual three-source policy
operation introduced by the separate stacked `source_routes layout`
development branch. Previously, users could sketch a valid mapping but
had to reconstruct the five technical CLI arguments themselves.

The operator must first use the **authorized Pi terminal** to check
`python3 -m audiohub.source_routes --format text slots`. The browser
does not observe the private Pi route policy or trust Bluetooth source
identities. The operator selects the **two current Bluetooth input slots**
from that separately verified terminal view, then chooses target LAN,
BT A and BT B slots in the existing what-if planner. Current slots
begin as `unknown`, never with assumed device assignments.

Only when exactly two distinct current slots and a valid target
permutation of all three technical slots are selected, an ordinary
read-only textarea displays a safe, fixed-slot command, for example:

```sh
PYTHONPATH=/opt/audiohub/src python3 -m audiohub.source_routes --format text --preview layout music music tablet tablet laptop
```

The user may manually copy that instruction **to the authorized Pi
terminal**; the web page does **not** execute the command, open a
network socket, call the device, change a source, identify a sender,
pair Bluetooth, authenticate the owner or write a private file. Only
the separately authorized terminal can evaluate the actual route
policy and issue its revision token. That token is **never generated,
accepted, predicted or inserted by this browser feature**. A future
route change still requires an entirely separate, local, explicitly
confirmed revision-guarded action. No confirmation command is
generated by the page. This is not phone-based onboarding or a
remotely authenticated control panel.

The command field clears immediately upon an invalid/incomplete
target, duplicate/unknown old source slot, or reset. Reset also
returns both manually entered *current* input slots to unknown. The
command is built exclusively from the existing fixed
`music/laptop/tablet` allowlist, not user-supplied names, MAC
addresses, IPs, device names or arbitrary shell text. A translation
change keeps the command's technical words invariant while
translating labels and validation feedback. Existing controls for
input labels, mock volume/EQ, status, and owner device settings
are unaffected. The explicit developer preview remains
`UNVERIFIED_ALPHA_TEST_ONLY` until legal and real hardware acceptance.

## Browser-only three-source routing layout planner (unmerged draft)

The existing five-language web preview now includes a responsive **three-input
routing example planner**, separate from real device status. A user may select
one LAN mixer slot and optionally assign two **anonymous example** Bluetooth
sources to `Input 1`, `Input 2` and `Input 3`. If two sources claim the
same slot, the preview immediately rejects the layout and does not display it
as valid. Unassigned Bluetooth placeholders are allowed; LAN must always
reserve exactly one of the three slots. A reset button restores the
initial sample mapping (LAN = Input 2, example Bluetooth sources = 1 and 3).
The rendered slot list and validation messages update in all five languages.
Keyboard-accessible native selects, explicit labels, non-color-only error
text, a live validation status and responsive vertical mobile layout are
used. Rendering only fixed translated labels via `textContent` avoids
injecting browser or device identifiers into the display.

**Deliberate safety and product boundaries:** This is a **what-if example,
not a snapshot of the Pi routing policy**. It does not read actual source
assignments, search or pair Bluetooth devices, authenticate senders, change
volume/EQ, open a socket, write local storage, download private names, submit
an HTTP request or change real routes. Neither a valid sample layout nor the
public read-only route counts proves that any device is paired, connected or
audible. The selector's source 1/2 names are placeholders, **not real BT
identities or MAC addresses**. Browser input-name preferences and sample
mixer volume settings remain independent and untouched when the example
layout is reset. A real route operation continues to require an authorized
local audiohub-user terminal, a private `source_routes --preview` at the
current policy revision and a separate, revision-guarded confirmation. The
web preview cannot issue that confirmation. Remote-phone access still
requires owner-authenticated onboarding; it is not provided by this PR.

The channel-card capability hints no longer imply that the `music`,
`laptop`, and `tablet` technical slot IDs permanently bind particular
transport types. The new wording distinguishes possible flexible assignment
from verified live audio and remains neutral about which input a real device
uses.

## Generic audio input display names (AH-004, draft PR #26)

The UI now presents **Input 1, Input 2, Input 3**, not mandatory
phone/laptop/tablet device classes. Each channel card provides a text input
to preview a human-defined, distinct 1–32-character display name, such as
"Living room TV", "Games console" or "Work PC". Locales `en/de/es/fr/it`
include input names, transport-capability hints, validation and honest
save-status text. Names are rendered through `textContent` (never HTML).

**Critical scope distinction:**

1. **Browser preview:** Custom names are kept in that browser's
   `audiohub.preview.input-labels.v1` localStorage only. They survive
   page reloads on that same browser, but are not Pi device settings,
   are not synced between browsers, and do not control audio routing.
   Preview volume/mute/EQ controls also remain nonfunctional mock UI.
2. **Pi-local storage model:** `src/audiohub/input_profiles.py`
   provides strictly validated private (0700 directory, 0600 file)
   atomic user-owned labels, accessible **only by a local console**
   to the Linux `audiohub` user. For engineering bench setup:
   `python3 -m audiohub.input_profiles show` or
   `python3 -m audiohub.input_profiles set music "Living room TV"`.
   Only stable slot IDs are accepted, never source IPs, MACs or
   new PipeWire node names. This console model is **not** wired into
   the browser or an authenticated API yet.
3. **Actual transport assignment:** Current test code supports up
   to two Bluetooth input nodes (default internal `music/tablet`)
   and a manually opted-in LAN PCM receiver (default internal `laptop`).
   Changing a display name **does not** bind the named device or change
   the transport/slot routing. Owner-authenticated source selection,
   slot reassignment, phone setup and recovery remain P0/P1 gates.

No new HTTP mutation endpoint was added. Anonymous status stays redacted,
local-only and strictly read-only. A future owner API must first prove
per-device claim, authentication, CSRF protection, authorization for each
source and validated local settings persistence. The SD diagnostic report
does **not** contain user-defined names.
