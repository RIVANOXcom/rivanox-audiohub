# Offline SD-card diagnostic for the first Raspberry Pi 4 audio test

**Status:** Operator-only S2 native Pi4 test package is built and available
for the exact successful GitHub source/native CI SHA. No real Pi4 test has
yet proven it boots or produces Edifier sound. It is NOT a production release,
a hardware pass or an approved secure owner login.

## Why it exists

The Pi4 image has no validated Wi-Fi onboarding, is not supposed to be
connected to a trusted home network, and does not enable SSH. If a headless
Bluetooth/USB audio test fails, the operator cannot otherwise see whether
the Pi booted, whether the USB output was discovered or whether a Bluetooth
route was created.

This proposal installs a one-time, private-network-isolated systemd service
which, only if `/boot/firmware` is an actual mounted partition, writes
`AUDIOHUB-TEST-REPORT.json` **to the readable boot partition of the SD card**.
The operator can shut down the isolated test Pi, remove the card after power
is off, mount it on their computer and inspect this small JSON file. This
does not require Internet access, Ethernet, home Wi-Fi, SSH, passwords or
an application.

## Identify which exact test image booted (new unverified alpha)

The installed image now carries a fixed **nonsecret** build identity at
`/etc/audiohub/build-identity.json`, generated from the checked-out
source commit, pinned `pi-gen` SHA, and GitHub Actions native image-run
number (or `null` for an independently built image). The one-time
offline FAT report includes an `image_identity` object containing
only these immutable source/build references. This helps an operator
distinguish actual test-SD versions when comparing several boot cards
and correlates a physical observation with its exact GitHub source
and native image job. It does **not** identify a person, network,
USB device, SD serial or Bluetooth peer. The image-builder refuses a
CI SHA mismatch or uncommitted tracked source so a dirty build is
not mislabeled with an unrelated Git commit.

If build metadata is absent, malformed, replaced by a symlink,
writable by other users, not a single ordinary file, or contains
unapproved claims, the report explicitly shows
`{"image_identity":{"status":"unavailable"}}` instead of inventing
a source revision. Its root-owned, bounded, nofollow reader does not
modify the source file. The report still carries
`hardware_accepted: false`, `owner_authenticated: false` and
`UNVERIFIED_ALPHA_OFFLINE_TEST_ONLY`. **The identity is not a
cryptographic attestation:** anyone with physical SD write access
could replace the image. Independently verify downloadable ZIP/image
hashes, physically identify the test SD and preserve the old SD for
rollback. No phone provisioning, auto-boot approval, network service,
image flashing or hardware GO is added.

## What the report contains

At startup and ~30, 60, 120, 180, 300 and 600 seconds later, the diagnostic
snapshots (maximum seven) record:

- Whether `audiohub`'s PipeWire runtime summary exists and is recent.
- Whether the audio supervisor reports a USB audio output.
- Number of discovered Bluetooth audio sources (capped at 2).
- Number of active routes (capped at 3).
- Number of valid, recognized virtual audio channels (capped at 3).
- Whether the OS has a Bluetooth controller path (true/false).

It also contains fixed flags: `hardware_accepted: false`,
`owner_authenticated: false`, `phone_wifi_provisioned: false`,
and a clear `UNVERIFIED_ALPHA_OFFLINE_TEST_ONLY` marker.

**It does not contain** Bluetooth MACs, IP addresses, source identifiers,
device serials, network names, Wi-Fi secrets, login tokens, USB product
serials, personal data or raw PipeWire dumps. Runtime data is read with
bounded size and no symlink following; the report is generated by strict
field whitelisting, and is capped at 4096 bytes.

## Reading USB *routing*, not merely finding a USB speaker

For the **new five-file S2 operator ZIP** (not older four-file alpha
bundles), the existing [standalone offline report viewer](../web/boot-report-viewer.html)
is included directly as
`AUDIOHUB-OFFLINE-REPORT-VIEWER.html` **next to the native image**. No
second network download or Pi login is required to understand first-boot
results. The same source HTML continues to be packaged in the native
rootfs. The `PREVIEW-MANIFEST.json` includes the exact viewer SHA256 and
byte size, and the existing `scripts/release_bundle_audit.py --zip`
operator verifier now checks this fifth file and the image together.
Previous **four-file** ZIPs remain supported but lack the bundled viewer.

On a trusted PC, download the authenticated ZIP, check its **outer** SHA256
against the exact provider digest, extract it, compare the viewer's SHA256
against `PREVIEW-MANIFEST.json.offline_viewer.sha256`, and open the HTML
**locally**. After safely powering down the isolated Pi, manually select
`AUDIOHUB-TEST-REPORT.json` from the spare SD boot partition using the
viewer's local file picker. The report is produced by the Pi **after boot**
and is NOT a prefilled or imported report inside the ZIP. Never upload a
report, enter phone credentials or connect a trusted network to the test
Pi. Keep old SD and private WAV/EQ/non-WAV backups intact, and do not treat
a reported USB route as evidence of actual audible sound.

The viewer's existing **USB output and direct audio link** row now
distinguishes four outcomes:

- **USB device not reported:** no physical USB output found in the last
  observation; inspect the Edifier USB connection only on the isolated bench
- **USB found; route not checked:** runtime is stale or the older file lacks
  strict link-health fields; no link claim is possible
- **USB found; route needs attention:** hardware is reported but either
  `usb_audio_route_ready` is false or zero direct EQ-to-USB links were
  inspected; do not assume sound or change routes without authorized access
- **Direct link reported (not sound):** recent runtime reported readiness and
  at least one direct EQ-to-USB link; this is **NOT** evidence of audible
  left/right stereo, exactly the music link, or a safe sound level

The last snapshot still supplies current USB route, Bluetooth and runtime status.
To reveal intermittent first-boot faults without a Pi login, the existing
observation count now also summarizes all one to seven validated USB presence
samples: always present/absent in samples, appeared late, disappeared, or
changed in both directions. A single sample is insufficient for a trend.
Five-language guidance recommends only isolated authorized cable/power checks.
The sampled observations do NOT prove continuous sound or S3 acceptance; no
device IDs, USB identifiers, private WAV names or arbitrary source JSON
text are shown. Strict boolean
and bounded direct-link count validation prevents fabricated ready states;
older compatible observations remain labelled **not checked**. The viewer
offers relevant next steps in all five existing languages, never owner,
hardware or release GO. For a real low-volume speaker test, human observation
and a separately approved safe operator login (AH-005) are still required.

## Safety and limitations

The report is **not cryptographically signed**, can be modified by anyone
with physical SD-card access, and can be absent if boot stalls, the FAT
partition is not mounted or the service fails. Do **not** use it as a
security/acceptance proof. A `usb_audio_detected: true` flag means a
matching PipeWire output was reported, **not** that an Edifier produced
audible sound. A `bluetooth_audio_sources: 1` count does **not** prove
authorization or actual A2DP audio.

The root service starts independently of audio playback, never opens a
network client or DBus, has `PrivateNetwork=yes`, and can write only to
`/boot/firmware` under its sandbox. It takes at most ten minutes of
snapshots, then exits. Failures do not block Bluetooth or PipeWire services.
A new boot overwrites the previous report atomically; copy it off the card
before retesting. Avoid abrupt power cuts while the SD is writing; use
a separate test SD, not a production appliance.

The image pre-export audit blocks a build if the diagnostic source or
enabled sandboxed unit is missing. Unit tests check redaction, stale or
malformed metrics, symlink rejection, bounded report size, repeated
snapshots and rootfs safety. They are source/packaging tests, NOT Pi4
hardware proof.

## For the operator

1. Use a **newly verified experimental image that explicitly includes this
   feature**. The 5 November 2026 artifact #13413143397 predates this
   change and **will NOT produce this report**.
2. Power the Pi 4 from a reliable adapter with the Edifier USB speaker
   attached, no Ethernet and no real Wi-Fi credentials.
3. Try Bluetooth `AudioHub` pairing and low-volume test music. Observe
   whether actual speaker sound plays. Keep the test Pi powered for about
   ten minutes to collect all snapshots.
4. Power off and disconnect the Pi safely. Remove its spare microSD and
   read `AUDIOHUB-TEST-REPORT.json` from the card's **boot partition** on
   a Windows/macOS/Linux computer. If missing, report 'missing', not 'failed
   boot' without additional evidence.
5. Provide the sanitized JSON plus whether the Pi visibly booted, whether
   pairing succeeded, whether speaker sound was audible and what happened
   after reboot. No private identifiers needed.

This feature is intentionally not integrated with secure phone ownership
or WLAN provisioning. Release gates G2/G3/G4/G7/G8 and G10 remain open.

Project: `PJ2611-0001:R001`; AH-009 requirement 3275 and
AH-001 requirement 3267. No physical test signoff or official release.

## Compare a removable-SD report with the chosen package (offline)

The offline HTML viewer now shows the strictly validated **public source
commit SHA** in current Pi4 FAT first-boot reports. After independently
verifying the authenticated test ZIP and inner IMG.XZ checksums, paste the
`source_commit_sha` from that ZIP's `PREVIEW-MANIFEST.json` into the
viewer's expected-source field. MATCH, MISMATCH, invalid input, or missing
image identity is shown in all five languages. On **MISMATCH: STOP** and
check which spare SD booted before any physical acceptance step. The
comparison performs no network request, credential action, Pi write or
external report upload. Older valid reports without identity still load.

**The FAT report is mutable and unsigned:** even a matching SHA proves
neither authentic boot, real stereo output, S3 nor release authorization.
The original ZIP and image integrity and real human observations are
separate acceptance requirements.

## Choose the matching package manifest directly in the offline viewer

For S2 packages including the updated local viewer, the operator can open
`PREVIEW-MANIFEST.json` from the **same independently SHA256-verified ZIP**
in a second file picker. The viewer checks the alpha schema, test-only
flags, bounded public source SHA and viewer provenance, then fills the
expected source SHA without manual transcription. Invalid, renamed or
oversized manifests clear the source field; a manual override cancels any
pending asynchronous manifest read. This avoids accidental manual SHA
mistypes while leaving older reports and manual typing supported.

The offline viewer also presents three localized **before-flashing gates**:
original SD and all owned media backups, advance approval of a safe
power-down method (AH-005 separate owner), and host-verified ZIP/image/
viewer hashes. None is approval to flash. **The viewer does not hash the
archive, attest to a boot, prove Edifier sound or grant device access.**

## Optional two-boot USB troubleshooting on a trusted PC

For later owner-authorized physical investigations, archive the earlier
AUDIOHUB-TEST-REPORT.json before a subsequent boot overwrites it.
The bundled offline HTML viewer can locally compare two such files using
the exact same strict parser. It reports only source-matched, anonymous
USB direct-link and sampled USB-presence changes, or refuses to imply
comparability for missing/mismatched source SHA or package identity.
This feature does NOT authorize reboot, bypass the AH-005 safe shutdown
dependency, prove audible sound or treat unsigned FAT data as attestation.
