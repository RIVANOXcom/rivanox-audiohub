# Offline SD-card diagnostic for the first Raspberry Pi 4 audio test

**Status:** Source-only proposed alpha feature until a successful ARM64 image
build and a real Pi4 test prove it runs. It is NOT a release, a hardware pass,
a secure owner login, or a test of speaker sound quality.

## Why it exists

The Pi4 image has no validated Wi-Fi onboarding, is not supposed to be
connected to a trusted home network, and does not enable SSH. If a headless
Bluetooth/USB audio test fails, the operator cannot otherwise see whether
the Pi booted, whether the USB output was discovered or whether a Bluetooth
route was created.

This proposal installs a one-time, private-network-isolated systemd service
which, only if `/boot/firmware` is an actual mounted partition, writes
`AUDIOHUB-TEST-REPORT.json` **to the readable boot partition of the SD card**.
The operator can shut down the isolated test Pi, remove the card after power
is off, mount it on their computer and inspect this small JSON file. This
does not require Internet access, Ethernet, home Wi-Fi, SSH, passwords or
an application.

## What the report contains

At startup and ~30, 60, 120, 180, 300 and 600 seconds later, the diagnostic
snapshots (maximum seven) record:

- Whether `audiohub`'s PipeWire runtime summary exists and is recent.
- Whether the audio supervisor reports a USB audio output.
- Number of discovered Bluetooth audio sources (capped at 2).
- Number of active routes (capped at 3).
- Number of valid, recognized virtual audio channels (capped at 3).
- Whether the OS has a Bluetooth controller path (true/false).

It also contains fixed flags: `hardware_accepted: false`,
`owner_authenticated: false`, `phone_wifi_provisioned: false`,
and a clear `UNVERIFIED_ALPHA_OFFLINE_TEST_ONLY` marker.

**It does not contain** Bluetooth MACs, IP addresses, source identifiers,
device serials, network names, Wi-Fi secrets, login tokens, USB product
serials, personal data or raw PipeWire dumps. Runtime data is read with
bounded size and no symlink following; the report is generated by strict
field whitelisting, and is capped at 4096 bytes.

## Safety and limitations

The report is **not cryptographically signed**, can be modified by anyone
with physical SD-card access, and can be absent if boot stalls, the FAT
partition is not mounted or the service fails. Do **not** use it as a
security/acceptance proof. A `usb_audio_detected: true` flag means a
matching PipeWire output was reported, **not** that an Edifier produced
audible sound. A `bluetooth_audio_sources: 1` count does **not** prove
authorization or actual A2DP audio.

The root service starts independently of audio playback, never opens a
network client or DBus, has `PrivateNetwork=yes`, and can write only to
`/boot/firmware` under its sandbox. It takes at most ten minutes of
snapshots, then exits. Failures do not block Bluetooth or PipeWire services.
A new boot overwrites the previous report atomically; copy it off the card
before retesting. Avoid abrupt power cuts while the SD is writing; use
a separate test SD, not a production appliance.

The image pre-export audit blocks a build if the diagnostic source or
enabled sandboxed unit is missing. Unit tests check redaction, stale or
malformed metrics, symlink rejection, bounded report size, repeated
snapshots and rootfs safety. They are source/packaging tests, NOT Pi4
hardware proof.

## For the operator

1. Use a **newly verified experimental image that explicitly includes this
   feature**. The 5 November 2026 artifact #13413143397 predates this
   change and **will NOT produce this report**.
2. Power the Pi 4 from a reliable adapter with the Edifier USB speaker
   attached, no Ethernet and no real Wi-Fi credentials.
3. Try Bluetooth `AudioHub` pairing and low-volume test music. Observe
   whether actual speaker sound plays. Keep the test Pi powered for about
   ten minutes to collect all snapshots.
4. Power off and disconnect the Pi safely. Remove its spare microSD and
   read `AUDIOHUB-TEST-REPORT.json` from the card's **boot partition** on
   a Windows/macOS/Linux computer. If missing, report 'missing', not 'failed
   boot' without additional evidence.
5. Provide the sanitized JSON plus whether the Pi visibly booted, whether
   pairing succeeded, whether speaker sound was audible and what happened
   after reboot. No private identifiers needed.

This feature is intentionally not integrated with secure phone ownership
or WLAN provisioning. Release gates G2/G3/G4/G7/G8 and G10 remain open.
