# Authenticated Windows audio sender — unresolved architecture (AH-002/AH-005)

**Decision status: PROPOSED ONLY. No security architecture is approved or deployed.**

## Threat / blocker

Legacy Windows Scream sends plain PCM over UDP. Its packets have a sample
format header, **not** a message authentication code, identity, nonce, replay
counter, or encryption. Source-IP filtering and a manually chosen host address
are not cryptographic authentication; an attacker able to spoof the sender on
the same LAN may inject audio or exhaust resources. The current
`audiohub.network_laptop` is deliberately an unsafe opt-in prototype: the
image does not start it, and it must never become a default consumer service
in its current state. The Pi owner's Bluetooth pairing does not establish
a Windows laptop's network sender identity.

## Required security properties

1. Owner authentication and a visible explicit **add laptop** action must
   precede all transport enrollment. No fixed shared setup code, printed
   universal password, or auto-accept rule.
2. A laptop must receive a unique, independently revocable cryptographic
   identity; enrollment must be short-lived, bound to an authorized owner
   session and resistant to replay. A Windows IP address alone is not an
   identity.
3. No plaintext Scream UDP port may be exposed on Wi-Fi/LAN while a secured
   production receiver is active. Attackers on the physical LAN must not be
   able to bypass the authenticated entry point with spoofed packets.
4. Lost/revoked laptop credentials stop playback promptly. The receiver must
   tolerate unsolicited packets, key rotation, reconnect, unexpected reboots,
   and denial-of-service while preserving Bluetooth audio availability.
5. Limit privileges: only the isolated ingress component controls encrypted
   sender access. Audio routing remains under the unprivileged PipeWire user;
   no network client receives OS or web administration rights.
6. Store secrets in owner-protected OS facilities, not source, test fixtures,
   SD-card image templates, public status endpoints, logs or release assets.
   Provide audited recovery and wipe/re-enrollment behavior.
7. Include negative tests for forged source IP, invalid certificate/key,
   expired enrollment, cross-owner/device reuse, revocation, replay attempts,
   misrouted USB output and concurrent Bluetooth traffic.

## Candidate architectures (no decision yet)

**Option A — Encrypted point-to-point tunnel, for example WireGuard.**
Create a distinct authorized peer after secure device ownership has been
established. The Windows audio driver sends its ordinary unicast Scream
packets to the Pi's *tunnel* IP. Restrict UDP 4010 to the correctly
authenticated tunnel ingress via host firewall and interface-specific binding;
do not expose it via a physical LAN interface. Pin peer allowed addresses and
prevent bypass from any other peer. Design key provisioning, device
revocation, firewall rollback, and recovery before deployment. A tunnel
alone does not authenticate Scream packets within the tunnel unless the
network configuration *ensures* only the enrolled peer can reach the port.
No tunnel, keys, installer, firewall rules or privileged actions have been
added in this prototype. Windows installation friction may conflict with
flash-and-boot consumer UX.

**Option B — Authenticated audio sender/relay.** Build a Windows companion
which accepts local audio and transmits it in an authenticated encrypted
session (for example TLS with a separately verified device key); the Pi
only processes decrypted PCM from the enrolled sender. Define codec,
latency, playback clocks, buffering, session rekey, replay control, and
revocation. This needs additional Windows client development, dependency
licensing, support and full security review. It does not make the current
unmodified Scream UDP stream authenticated.

Both options depend on **AH-005 owner claim**. Neither can be declared
working from a unit test or topology preflight. No third-party keys or
credentials are generated by this decision draft.

## Engineering recommendation and decision gate

Investigate Option A first in an isolated test network because it can
carry an unmodified Scream UDP sender; separately measure the Windows
installation burden and recovery security. Do not commit to production
until the project owner chooses an enrollment UX/security architecture,
and design tests demonstrate a fail-closed tunnel/firewall configuration.
Option B is the fallback if transparent Windows onboarding or lower
latency requires a purpose-built sender.

**Required owner decision before any production activation:** select a
security/enrollment design, approve the end-user installation steps,
decide permitted network exposure, and authorize the corresponding
controlled hardware security acceptance. Until then, keep
`--unsafe-lan-test` manual-only on a trusted isolated LAN; never treat an
IP allowlist as proof of sender identity. The current pull requests do not
alter permissions, firewalls, services, secrets or production devices.
